# 保存失败的反馈与兜底

> 状态：待实现（方案已定，尚未动代码）
> 关联：与 `wip/r4-r5-0.8` 分支无代码冲突；PRD 编号待该分支的 R12 合入后再补为 R13

---

## 1. 问题

### 1.1 用户反馈

2026-10-23，一位用户报告（原话）：

> 是我这边点保存直接没用
> 我关掉再打开，之前写的就没了
> 保存直接没起作用
> 才没有返回
> 刚才我这边保存不了，点了保存然后点转换退到外面 这时候写的东西还在，但关掉再打开就没了

### 1.2 症状与代码的对应关系

旧保存链路（自首个提交 `5da8b55 init: mvp` 起未变，**不是某次发版的回归**）：

```ts
flushEditingDraft();
exitEdit();          // ① 先退出编辑
await persist();     // ② 这里抛错 → 后面三行全被跳过
render();
showToast("已保存");
```

`persist()` 内没有任何 try/catch，写盘失败会变成未处理的 Promise 拒绝，函数在此中断：

| 用户描述 | 实际发生 |
| --- | --- |
| 点保存直接没用 | 没有 `render()`、没有 toast，DOM 停在编辑态 |
| 才没有返回 | 回调在 `await` 处断掉，永远没有结果 |
| 点转换退到外面，写的东西还在 | `exitEdit()` 在抛错前已执行，随后的重绘把内存内容显示出来 |
| 关掉再打开就没了 | 磁盘上一个字节都没写 |

**问题的性质**：把「磁盘写不进去」伪装成了「保存成功」，比单纯的保存失败更严重。

### 1.3 具体原因

该用户的数据文件**没有写入权限**（已由其自行排查确认）：读正常、写报 `os error 5`。路径合法、文件存在，因此应用能正常加载，只在保存时失败。

### 1.4 连带的两个隐患

- `read_data()` 解析失败时静默回退默认数据，用户看到三个演示块，**下一次保存就把真实文件覆盖**（最坏路径）
- `boot()` 载入失败同样完全静默

## 2. 业界做法对照

| 做法 | 代表 | 失败时的处理 |
| --- | --- | --- |
| 自动保存，无按钮 | Apple Notes、Obsidian、Typora、Notion | 不弹窗；角落显示「已保存 / 无法保存」小标记，可点重试 |
| 有保存按钮，失败给动作 | Word / Excel、VS Code | Word 弹「另存为」换位置；VS Code 给「重试 / 另存为 / 查看原因」 |
| 写入与同步分离 | Apple Notes、Notion | 本地写入近乎必然成功，只有云端同步失败才提示 |

共同点：

1. **失败处理的目标是保住内容，不是告知**。只告诉用户「保存失败」等于只说问题不说解法。
2. **状态用角标，不用 toast**。Notion 的保存状态是标题栏旁一小段灰字，从不弹出「保存成功」。
3. **只有「内容可能丢失且用户即将离开」时才打扰**。

> 参考 Sticky Notes：它不提示是因为没有保存按钮（每次输入 debounce 后写本地库），且其静默属于**短板**而非范本——「便签内容无故消失」的投诉长期存在。它的做法不应照抄。

## 3. 方案

三层：**角标（状态）→ 草稿（内容保全）→ 不做关窗拦截**。

### 3.1 角标：状态化的保存反馈

位置：`.shell` 内右下角，`position: absolute; bottom: 6px; right: 8px`，不影响布局，空闲时不渲染。

| 状态 | 显示 | 行为 |
| --- | --- | --- |
| 空闲 | 不渲染 | — |
| 已保存 | `✓ 已保存`（10.5px 灰字） | 1.2s 后淡出并清零 |
| 未保存 | `⚠ 未保存 · 重试`（超限色 `#f0a8a8`） | 常驻不消失；`title` 放完整错误；点击重试 |

- **成功也走角标，不再用 toast**：否则会出现「成功大声喊、失败小声说」的错位；且 400px 置顶窗每次保存都被 toast 盖住 1.4s 打扰不小。
- toast 保留给一次性事件（已复制、已删除、暂无标题）。分工：**状态归角标，事件归 toast**。
- 角标状态存在变量中（`saveState` / `saveError`），`render()` 按状态输出；淡出用定时器直接改 `classList`，不整体重渲染，避免打断输入焦点。

### 3.2 草稿兜底

存 **`localStorage`**，键 `pinboard.draft`，值 `{ data, at }`。

选择理由：写同目录文件没用（同目录不可写正是失败原因）；`localStorage` 同步写、无需 await、零 Rust 改动、与主文件路径无关，且只需活到下次启动。

三个时机：

- **失败即写**：`persist()` catch 里先 `setItem`，把内容放进安全位置再考虑提示
- **成功即清**：写盘成功立刻 `removeItem`，不留过期草稿
- **启动自愈**：`boot()` 发现草稿 → 用草稿覆盖内存数据（磁盘版本必然更旧）→ 立即重试一次写盘
  - 成功：清草稿，角标闪 `已恢复上次未保存的内容`
  - 仍失败：角标常驻 `未保存`

自愈效果：用户修好文件权限后，只要开一次应用，内容就自动回磁盘，不需要再点保存。

### 3.3 不拦截关窗

有草稿兜底后**不需要**「内容未保存，仍要关闭？」确认框。这也是上述应用敢「不提示」的真正原因——它们有 journal / WAL。拦截 `close-requested` 再回前端确认改动大、收益已被草稿替代，不做。

### 3.4 保留的三项（与提示无关，属于内容保全）

- 保存改为**先落盘成功再退出编辑**，失败则留在编辑态，用户可重试或把内容拷走
- Rust `read_data()` 解析失败时先备份为 `*.json.broken` 再返回错误，避免下次保存覆盖真实数据
- `write_data()` 错误信息带上文件名：`写入失败（pinboard.json）: 拒绝访问。 (os error 5)`，便于定位

### 3.5 载入失败仍用 toast

文件损坏时界面会显示三个演示块，不做解释用户会以为数据没了。此处保留一次 toast（`载入失败：…（已显示默认内容）`），不塞进角标。

## 5. 验收

- [ ] 正常保存：角标闪 `✓ 已保存` 后消失，正文不被遮挡，无 toast
- [ ] 把数据文件设为只读 → 保存：留在编辑态、内容仍在、角标常驻 `⚠ 未保存 · 重试`、hover 可见原因
- [ ] 只读状态下关闭应用再打开：内容仍在（草稿恢复），且启动时自动重试写盘
- [ ] 解除只读后再打开：内容自动落盘、草稿清空、角标显示 `已恢复上次未保存的内容`
- [ ] 正常路径从不产生草稿：`localStorage` 中无 `pinboard.draft`
- [ ] 文件损坏：载入失败 toast 出现，原文件被备份为 `*.json.broken`

---

## 6. 不做 / 后续

- **自动保存（输入后 debounce 落盘，保存按钮语义改为「完成并收起」）**：会改变交互习惯，单独立项讨论，不混入本批。
- **设置页显示「此位置无法写入」并提供「换一个位置」按钮**：这是同类问题的自助解法（`chooseDataFilePath` 已存在），可作为后续增强；本批先靠角标的 `title` 暴露原因。
